---
title: Sessions and prefix pools
---

When you send a follow-up turn, the server should ideally already have your
conversation's KV cache sitting in a slot, and continue from it rather than
re-reading the whole conversation. Stock `llama-server` decides which slot to
use by its own heuristics, and with several conversations in flight it does not
always pick yours.

The opencoti engine can be told directly. xollama does that for you.

<Note>
  This page is about the opencoti engine. On stock `llama.cpp` nothing on this
  page is sent, and the request is byte-for-byte what upstream Ollama would
  send.
</Note>

## Session affinity

A **session** is one conversation. Give it a name and the engine returns it to
the slot already holding its cache.

It is **on by default** and you do not have to do anything. xollama derives the
name from the part of a conversation that does not change as it grows — the
model, the system prompt, the tool definitions and the first user message — so
the same conversation gets the same name on every turn, and different
conversations get different names.

### Turning it off, per server or per model

<Tabs>
<Tab title="Server">
For a service, set it where the service reads its environment — a systemd
drop-in on Linux, or the system environment on Windows:

```ini
# /etc/systemd/system/ollama.service.d/xollama.conf
[Service]
Environment="XOLLAMA_SESSION_AFFINITY=0"
```
</Tab>
<Tab title="One model">
In the Modelfile, which travels with the model:

```dockerfile
FROM gemma4:e4b

XOLLAMA {"version": 1, "session": {"affinity": true}}
```
</Tab>
</Tabs>

The model's own setting wins over the server's. That is the point of having
both: a server default that suits most of your models, and an override on the
one it does not suit.

Affinity is worth switching **off** for a model that answers unrelated one-shot
prompts. There is no conversation to return to, and naming each prompt a session
only adds bookkeeping.

### Naming a session yourself

Send `session_id` on `/api/chat` or `/api/generate` and yours is used instead of
the derived one:

```shell
curl http://localhost:22434/api/chat -d '{
  "model": "gemma4:e4b",
  "session_id": "review-pr-4172",
  "messages": [{ "role": "user", "content": "…" }]
}'
```

Two reasons to bother. First, if your conversation's opening legitimately
changes — you rewrote the system prompt, or compacted the history — the derived
name changes with it and you lose the slot; your own name does not. Second, if
two genuinely different conversations happen to share a model, a system prompt,
their tools *and* their first user message, they derive the same name and will
compete for one slot. That costs you the optimisation, never a correct answer —
each request is still served from its own prompt — but your own names avoid it.

`/api/generate` derives nothing, because a one-shot prompt has no stable opening
to derive from and naming every prompt separately would be worse than naming
none. If you know a series of generate calls belongs together, send
`session_id`.

<Warning>
  If affinity is off — on the server or on the model — a `session_id` you send
  is ignored rather than switching the feature back on. "Off" is the operator or
  the model publisher saying this model must not pin conversations to slots, and
  a field in a request is not the place to overrule that.
</Warning>

### The session's window

On opencoti with elastic admission (its default under xollama), a session is
booked a context window of its own, and xollama tells you what you got. Every
admitted response on `/api/chat` and `/api/generate` carries it, streamed or
not, and so do the OpenAI (`/v1/chat/completions`, `/v1/completions`) and
Anthropic (`/v1/messages`) routes:

```text
X-Context-Window: 16384
```

The header is the engine's, passed on as it is. A continuation of a live
`session_id` reports the window the session already holds. **No header means no
guaranteed window**: stock llama.cpp, an engine without elastic admission, or a
council turn whose first byte left before its window was booked. A council turn
reports its owner's window, the one all its members share.

The windows come out of the model's pool, which is its `num_ctx` × the slots at
load. How that pool is sized, and how several windows share it, is on
[Concurrent requests](/xollama/slots#how-the-context-is-shared).

To ask for a window, state it in `placement` (`client_placement_v1`) on
`/api/chat`. Do not use `options.num_ctx` for this: it sizes the model's
load, so changing it reloads the model.

```shell
curl http://localhost:22434/api/chat -d '{
  "model": "qwen3.6",
  "session_id": "lead-1",
  "placement": { "num_ctx": 32768, "num_ctx_min": 8192 },
  "messages": [{ "role": "user", "content": "…" }]
}'
```

The engine grants the whole window, or the largest it can between
`num_ctx_min` and `num_ctx`, and `X-Context-Window` says which. A window above
the model's maximum is clamped, never refused. A continuation ignores a new ask
and keeps the window it holds. To change it, resize it
(`POST /api/engine?model=<model>&endpoint=sessions/<id>/resize`), or close the
session (`endpoint=sessions/<id>/close`) or let it expire and ask again.

A window that should last only for this request, not be booked for the
session, adds `"num_ctx_hold": false` (`context_window_unbooked_v1`, listed by
`/api/xollama` when the engine takes it):

```json
"placement": { "num_ctx": 32768, "num_ctx_min": 8192, "num_ctx_hold": false }
```

The engine grants it the same way, and frees it when the request ends. The
`session_id` still keeps the request on its slot and prompt cache. A window the
session already holds stays held.

When not even `num_ctx_min` fits, a client that stated `num_ctx` is not queued.
The same goes for a turn attached to a pool of the client's own
(`placement.pool_id`), such as a worker of its own pool tree. Both are the client
driving the engine, so it gets the engine's answer at once:

```text
HTTP/1.1 429 Too Many Requests
Retry-After: 2
X-Context-Largest-Admissible: 4096
{"error":"admission rejected: context allocation exhausted (largest admissible 4096 < num_ctx_min 8192) …"}
```

Retry with a smaller window, or later. `X-Context-Largest-Admissible: 0` is a
figure too: nothing is free, so waiting only helps once another session lets
go of its window, and a client holding one of its own can release it. The
header is absent only when the engine named no figure: a worker refused because
its owner's window is full ("session allocation full …") is the client's cue to
grow or move its owner.
A request that states neither keeps ollama's contract, and waits for room. If
such a request could never fit its window, it gets a `400` naming the numbers
instead of waiting.

## Shared prefix pools

Everything xOllama does with opencoti's shared cache, in one place: [PolyKV](/xollama/polykv).

Several conversations usually start the same way: one system prompt, one set of
tool definitions, tens of thousands of tokens repeated once per conversation. A
**pool** keeps one physical copy and lets every conversation attend it.

```dockerfile
FROM gemma4:e4b

XOLLAMA {"version": 1, "session": {"affinity": true, "pool": true}}
```

or, for a whole server, `XOLLAMA_SESSION_POOL=1`.

A pool needs session affinity — it attaches to a session, so with no session
identity there is nothing to attach. Asking for `"pool": true` together with
`"affinity": false` in a Modelfile is refused when the model is created, rather
than accepted and then quietly doing nothing.

You do not have to compute anything. The engine works out how much of your
prompt matches the pool itself, token by token, so there is no shared-prefix
length to declare and get wrong.

### How a pool comes to exist

A pool is made of the prefix two conversations were **observed** to share, not
of one conversation that happened to be first.

The first conversation with a given system prompt is served normally and its
prompt is remembered. The second one is compared against it, token for token
from the start, and the run they agree on becomes the pool. Every later
conversation that opens the same way attaches to it instead of storing its own
copy.

Waiting for the second conversation is deliberate. A prefix that turns up once
and never again would otherwise cost a reserved sequence for the life of the
runner, spent on nobody. It also means the pool is exactly as long as the thing
actually being shared — which matters more than it sounds, below.

Nothing about this is on the critical path. It all happens after the response
has been sent, and anything that fails is logged and forgotten: the model then
behaves exactly as it did before pooling existed.

A prefix shorter than 256 tokens is not pooled at all. A pool costs a sequence,
and sharing a sentence does not repay that; sharing a system prompt and a set of
tool schemas repays it many times over.

<Note>
  **Why the pool is the prefix and not the conversation.** An earlier version of
  this took a snapshot of the finished conversation instead, which was simpler
  and wrong twice over.

  A conversation snapshot holds the prefix *plus the first question and the
  first answer*, and only the prefix can ever match anything. Measured against a
  live engine: a pool of 50 tokens serving a shared prefix of 29. The other 21
  cells were pinned for the life of the pool and could never be used.

  The second problem is worse, and only bites on sliding-window models. Once the
  conversation that built an over-long pool moves on, the pool is the sole owner
  of its cells, and the ones that fall outside its own window become reclaimable.
  A later conversation attaching to it can then land over a hole — degraded
  attention across the tokens after the prefix, with no error and no warning.

  Building the pool from the shared prefix itself removes both: the cells a
  newcomer needs are exactly the ones the pool's own window keeps alive.
</Note>

### How many pools

```ini
Environment="XOLLAMA_POLYKV_MAX_POOLS=4"
```

or `session.max_pools` in the Modelfile. The default is two.

Size it by **distinct system prompts**, not by conversations — conversations
sharing a prompt share a pool, which is the whole point. Two is enough for one
prompt plus a variant.

It is not free. Each pool reserves a sequence for the life of the runner, and on
a sliding-window model a reserved sequence costs its own window exactly as a
slot does. That cost is included in the memory xollama plans for, so a pooled
model is placed and evicted against the number it will actually hold — see
[Concurrent requests](/xollama/slots).

When more distinct prefixes turn up than there are pools, the least recently
used pool is released to make room — released first, then the new one created.
The engine holds a fixed number of pool seats and refuses a creation past the
last one rather than making room itself, so the order is the difference between
the replacement happening and the replacement failing.

### Models that keep recurrent state

Models that keep **recurrent state** — Mamba and RWKV, and the growing family of
hybrids that put an SSM, a short convolution or a linear-attention block beside
the attention ones: Jamba, Falcon-H1, Granite hybrid, LFM2, Nemotron-H,
Qwen3-Next, Qwen3.5, Kimi Linear and their relatives — are pooled, but only from
**chat** requests.

The difference is structural. A pool is a *prefix* of a cache, and that works
because an attention cache is a per-token record which can be cut anywhere.
Recurrent state is not: it is one rolling summary of everything seen so far,
with no "first N tokens" to hand out. The engine will share such a state only
when the match covers the pool **entirely** and the prompt is strictly longer.

That makes the pool's length the whole question, and it is why the length is
*measured* rather than inferred. Two conversations that both open "What is the
capital of France" and "What is two plus two" share two tokens more than the
template does, and a pool two tokens too long is a pool nothing can ever match:
the attach succeeds, shares nothing, and spends a reserved sequence while
looking like it works. So before a pool is created, xollama renders this
conversation's system prompt and tools against several stand-in user messages
that share no opening, and keeps only the tokens every rendering agrees on.
That is the template and nothing past it. The measurement can only come out
*short* — a shorter pool is still a prefix of every prompt that has it, and the
engine simply matches all of it.

Pooling on these models therefore needs a measured boundary, and the
measurement has to use the renderer that produced the prompt. Sometimes that is
the engine's template; more often it is ollama's own, because any model with a
renderer, a parser, harmony or a Modelfile `TEMPLATE` is rendered before it
reaches the engine. Both are covered: on the first, xollama asks the engine; on
the second, the probe renderings are made where the template lives and carried
down with the request. A request that can supply neither is not pooled on these
models, and the server log says once at load which model that applies to.

Measured on a hybrid model (LFM2.5, `lfm2`) against opencoti build
`opencoti-0.10.5-c7-2609200554001`, with two conversations that both open
"What is":

```
trimmed a shared prefix back to the template boundary  from_tokens=686 to_tokens=684
polykv: created pool 0 (seq 1, prefix_len 684, source 'tokens/slot')
polykv-pools: attached pool 0 — shared 684-token prefix (n_past -> 684)
```

684 created, 684 shared, and no `bug-2203` line. With the trim disabled the
same run pools 686 and the engine answers
`hybrid/recurrent target needs exact full-state share (P=684, pool state=686,
prompt=693) — skipping share (bug-2203)`. Those two tokens are the whole
difference between sharing and reprocessing.

<Note>
  **Multimodal loads are not pooled.** The engine refuses the create outright —
  `501, "This feature is not supported by multimodal"` — so a vision model gets
  no pool seats rather than seats it could never use. `--polykv-max-pools` is
  not passed at all on such a load, and the reason is logged once at load.
</Note>

### Seeing it

```sh
curl -s 'localhost:22434/api/engine?model=gemma4:e4b&endpoint=polykv/pools' | jq
```

Each pool reports its prefix length, how many conversations attached, and when
it was last used. See [Seeing what the engine did](/xollama/introspection).

<Note>
  Pools are held open deliberately rather than left to the engine's idle sweep.
  A swept pool is not an error — a conversation attaching to a pool that has
  gone away simply reprocesses its prompt in full — but it is also silent, and a
  feature that stops working without saying so is worse than one that is off.
  They are released when the model unloads.
</Note>

## Settings summary

| | Environment | Modelfile | Request | Default |
|---|---|---|---|---|
| Session affinity | `XOLLAMA_SESSION_AFFINITY` | `session.affinity` | — | on |
| Session name | — | — | `session_id` | derived |
| Shared prefix pool | `XOLLAMA_SESSION_POOL` | `session.pool` | — | off |
| Pools per model | `XOLLAMA_POLYKV_MAX_POOLS` | `session.max_pools` | — | 2 |
| Pool seats for a client's own pools | `XOLLAMA_POLYKV_CLIENT_POOLS` | `session.client_pools` | — | 0 |
| Pool to attach to | — | — | `pool_id` | chosen for you |

Most specific wins: the request names the session, the model decides whether
sessions are used at all, and the server decides for models that say nothing.
