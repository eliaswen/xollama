---
title: Tuning opencoti
---

The opencoti engine carries work that stock `llama-server` does not: compressed
KV caches, a KV window that spills to host RAM instead of failing, training-free
long-context extension, and a shared-prefix pool for multi-agent serving. This
page is what you can reach from xollama **today**, and — just as important —
what you cannot.

<Warning>
  Read [Choosing an engine](/xollama/engines) first. None of this does anything
  unless the load actually routed to opencoti.
</Warning>

## How settings reach the engine

xollama launches the engine as a subprocess and **passes its whole environment
through**. Every opencoti flag also has an environment twin, so that is the
configuration channel:

```shell
LLAMA_ARG_DCA=on xollama serve
```

Two consequences you need to hold on to:

1. **It is server-global, not per-model.** Every model loaded by that server
   gets the same setting. There is no per-model carrier for these yet — the
   `XOLLAMA` Modelfile directive currently carries only `engine` and
   `draft.spec_type`.
2. **An explicit flag beats its environment twin**, and xollama already passes
   a number of flags of its own. Setting the twin for one of those is silently
   inert — it will not warn, it will simply not apply.

These are the ones xollama sets, so their `LLAMA_ARG_*` twins do nothing:

`--cache-type-k` · `--cache-type-v` · `--flash-attn` · `--context-shift` ·
`--spec-type` · `--spec-draft-model` · `--spec-draft-n-max` ·
`--spec-draft-backend-sampling` · `--log-verbosity` · `-c` · `-np` · `-ngl` ·
`-b` · `-ub` · `-t` · `--main-gpu` · `--split-mode` · `--load-mode` · `--keep` ·
`--mmproj` · `--chat-template` · `--host` · `--port`

Anything else is yours.

3. **A flag with no twin at all** — `--override-kv` is the notorious one — is
   reachable through `XOLLAMA_ENGINE_ARGS`, which is appended to the engine
   command line verbatim. See [Passing your own engine flags](/xollama/engine-args).

## KVarN — KV cache compression

The KV cache is usually what runs out first. KVarN is opencoti's current
compressed KV representation, selected as a cache **type** rather than a
separate flag, at widths `kvarn2` through `kvarn8` (roughly, bits per value —
smaller is smaller and lossier).

It is reachable through Ollama's own variable, because xollama passes that value
through without an allowlist:

```shell
OLLAMA_KV_CACHE_TYPE=kvarn3 xollama serve
```

That sets K and V to the same type. To set them **separately**, or to set them
per model rather than per server, use the fork's own settings — see
[KV cache types](/xollama/kv-cache):

```shell
XOLLAMA_K_CACHE_TYPE=kvarn3
XOLLAMA_V_CACHE_TYPE=q4_0
```

### iSWA models need the ring set too

Gemma-4 and other sliding-window models keep a second, short-window cache — the
"ring" — alongside the global one. opencoti's own measurements put the ring at
roughly **90 % of the sliding-window excess**, so compressing only the global
half leaves most of the cost in place. The ring has its own cache types, and
xollama does not set them, so their twins are live:

```shell
XOLLAMA_K_CACHE_TYPE=kvarn3
XOLLAMA_V_CACHE_TYPE=kvarn3
XOLLAMA_K_CACHE_TYPE_SWA=q4_0
XOLLAMA_V_CACHE_TYPE_SWA=q4_0
```

or, per model, a `kv` block in the Modelfile.

K and V on the ring must both be KVarN widths or both plain; mixing is rejected
at boot. In opencoti's KLD tables a KVarN global with a plain `q4_0` or `q8_0`
ring beat KVarN on both halves at the same size, so this pairing is the one to
start from rather than an afterthought.

<Note>
  The older `turbo*` / `*_tcq` tiers are deprecated and frozen upstream of us.
  Use `kvarnN`.
</Note>

## Rolling-KV — the window that spills

"KV doesn't have to fit." Each layer keeps a device-resident window of recent
positions; the tail lives in pinned host RAM and is streamed back through the
attention kernel per tile and merged exactly. When everything fits, every layer
stays resident and the path is unchanged — **the feature only engages under
memory pressure**.

```shell
LLAMA_ARG_VRAM_TARGET=20000          # MiB budget; 0 = all free VRAM
LLAMA_ARG_KV_RESIDENCY_MODE=auto     # auto | head | window — leave it at auto
```

Spilled decode sits at the PCIe floor and scales linearly with the tail — no
cliff, but on consumer PCIe it is a last resort. Prefer compressing the cache
(above) and treat spill as the thing that keeps a load alive rather than a
performance feature.

While a window is spilled, context shift and prompt-cache reuse are guarded off
and requests are bounded at the context length.

### What the window costs on a slow link

Measured by opencoti on an RTX 3090 on a PCIe gen4 x4 link (6.4 GB/s), with
Ternary Bonsai 2 27B, engine c11 (`2610101328001`), a 131072-cell context,
`q4_0` keys and values, the drafter off, 256 generated tokens per depth. The
small card is simulated with `--vram-target`; the window arm adds
`--kv-rolling-window 256`, the resident arm has no cap and keeps the whole
cache on the card. Decode time in ms per token, lower is better:

| Card simulated | Prompt depth (tokens) | Window | Resident | Window against resident |
| --- | --- | --- | --- | --- |
| 8 GB, PTQ1_0 | 36.6k | 13.36 | 13.37 | 0 % |
| | 38.8k | 13.81 | 13.42 | +3 % |
| | 40.6k | 14.74 | 13.52 | +9 % |
| | 42.8k | 19.88 | 13.60 | +46 % |
| 10 GB, PQ2_0 | 95.7k | 17.69 | 17.70 | 0 % |
| | 97.7k | 18.06 | 17.79 | +2 % |
| | 99.4k | 18.50 | 17.82 | +4 % |
| | 101.8k | 20.46 | 17.92 | +14 % |

The first depth of each block is where the prompt just passes the part of the
cache the window keeps on the card (35584 cells at 8 GB, 94464 at 10 GB); each
further row is 2048 tokens deeper into the host part. The cost grows with that
depth and with the link: the 8 GB arm pays 46 % three steps in. Prompt
processing speed is the same on both arms.

The two arms do not hold the same memory. The window arm took 6474 MiB (8 GB)
and 8656 MiB (10 GB), the resident arm 8122 and 9268 MiB, so the resident
column is what a card with that much room gives, not a second way to fit the
simulated one.

## DCA — long context beyond the model's training length

Dual Chunk Attention splits attention into intra-chunk, successive and
inter-chunk position regimes and merges them exactly, so a model trained at one
context length serves multiples of it without retraining. It is a **launch-time**
toggle — the cache stores keys un-rotated, so it cannot be switched per request.

```shell
LLAMA_ARG_DCA=on
LLAMA_ARG_DCA_CHUNK_SIZE=8192    # the validated recipe
```

<Warning>
  **The part that makes DCA worth having is not reachable from xollama today.**
  Serving past the model's declared context needs the engine's
  `--override-kv <arch>.context_length=int:…`, which has no environment twin, so
  there is no way to pass it. And xollama clamps `num_ctx` to the model's own
  training context before the engine is ever launched, with a
  `requested context size too large for model` warning. So you can turn DCA on,
  but you cannot ask for the long context it exists to serve.
</Warning>

Turning it on within the native context is measurable but is not the use case.
Until this is plumbed, a genuine 4× context run has to be done against the
engine directly rather than through xollama.

## PolyKV — shared prefix pools for multi-agent serving

PolyKV is opencoti's umbrella name for the whole KV-capacity stack, and at its
centre is **SharedKVPool**: N agents attending *one physical copy* of a common
prefix — a shared system prompt and tool definitions — instead of N copies.

The boot half is reachable:

```shell
LLAMA_ARG_KV_UNIFIED=1          # one shared cell pool across slots
LLAMA_ARG_POLYKV_MAX_POOLS=4    # enables the /polykv/* control plane
```

<Warning>
  **The request half is half-built.** `session_id` is now sent, so session
  affinity works — see [Sessions](/xollama/sessions). `pool_id` is plumbed to
  the wire and gated the same way, but xollama does not yet create pools or
  launch the engine with pooling enabled, so nothing hands out an id to attach
  to.

  `--kv-unified` is now set by xollama itself when dynamic slots are on — see
  [Concurrent requests](/xollama/slots) — so the boot half of pooling no longer
  needs an environment variable. What is still missing is `--polykv-max-pools`
  and something to create a pool.
</Warning>

If shared-prefix pooling is what you came for, drive the engine directly for now.

## Other knobs worth knowing

| Setting | Variable | Notes |
|---|---|---|
| Sparse attention | `LLAMA_ARG_SPARSE_ATTN=on` | Quest-style block selector; `…_TOPK`, `…_RECENT`, `…_SINK` tune it |
| Elastic slots | — | Now a first-class setting: [Concurrent requests](/xollama/slots) |
| Admission gate | `LLAMA_ARG_ADMISSION_POOLLESS` | `enforced` by default — refuses with 429 before prefill rather than thrashing |
| GPU sharing | `LLAMA_ARG_GPU_SHARE_WEIGHT` | Compute share against co-resident opencoti servers on one GPU |
| RYS layer duplication | `LLAMA_ARG_REPEAT_LAYERS` | Quality experiment; absent means byte-identical to stock |
| Sampler placement | `LLAMA_ARG_SAMPLING_PLACEMENT` | `auto` routes from a measured crossover. Measured null on this fork's cell — leave it |

## Checking what actually took effect

Do not assume a variable applied. The engine echoes its boot configuration and
its **effective** KV state:

```shell
curl http://127.0.0.1:<engine-port>/props | jq .opencoti
```

That is the authority on which cache tiers, residency mode and DCA settings the
engine really ended up with — including anything auto-tier decided for you. The
engine's own `--help` is the authority on flag names and defaults; where it and
any document disagree, `--help` wins.

<Note>
  xollama gives the engine a private port and does not proxy `/props`,
  `/slots`, `/metrics` or `/polykv/*`. Read the port from the server log, or
  query the engine directly when you launch it yourself.
</Note>

## Summary — reachable or not

| Feature | From xollama today |
|---|---|
| KVarN cache widths | **Yes**, per half and per model |
| iSWA ring cache types | **Yes**, per half and per model |
| Asymmetric K vs V types | **Yes** |
| Rolling-KV window and VRAM target | **Yes** |
| Mixed-KV spilled-tail types (`-ctkt`/`-ctvt`) | **Yes**, no twin conflict |
| DCA on/off and chunk size | **Yes** |
| DCA past the model's native context | **Yes** — xollama writes the `--override-kv` itself and the clamp stands aside for it |
| Any engine flag with no environment twin | **Yes** — `XOLLAMA_ENGINE_ARGS`, appended last; see [Passing your own engine flags](/xollama/engine-args) |
| Session affinity (`session_id`) | **Yes** — on by default, see [Sessions](/xollama/sessions) |
| PolyKV pool creation | Boot flags only, and xollama does not set them yet |
| PolyKV per-request attach | Plumbed and tested; nothing hands out a pool id yet |
| Elastic slots and the shared cell pool | **Yes** — on by default, per server or per model |
| Sparse attention, admission, RYS | **Yes** (boot env) |
| Cache types per model | **Yes** — and two models that disagree get their own engine |
| The rest of it per model instead of per server | **No** — server-global only, for now |
| Engine introspection (`/props`, `/slots`, `/polykv/*`) | **Not proxied** — query the engine directly |
